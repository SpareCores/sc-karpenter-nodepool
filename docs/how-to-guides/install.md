# Install the controller

This guide installs sc-karpenter-nodepool into a cluster that already runs
Karpenter (self-managed, or a managed flavour such as EKS Auto Mode), with the
Helm chart. To try it out first without a cloud account, follow the
[kind quickstart](../tutorials/kind-quickstart.md).

## Before you start

- A cluster with a Karpenter that serves `karpenter.sh/v1` NodePools (core
  Karpenter v1.2 or newer) and a NodeClass kind of one of the
  [supported providers](#provider-notes). The controller only creates
  NodePools; Karpenter itself launches the nodes.
- Helm 3.8 or newer (OCI registries), and `kubectl` with cluster-admin rights:
  the chart installs a CRD and cluster-scoped RBAC.
- Outbound HTTPS from the controller pod to the Spare Cores Keeper API
  (`https://keeper.sparecores.net`), and, only for EKS Auto Mode, to the AWS
  public price list (`https://pricing.us-east-1.amazonaws.com`). The controller
  needs **no cloud credentials**: it never calls a cloud API.

## Install with Helm

The chart is published as an OCI artifact next to each GitHub release. Pick a
version from the [releases](https://github.com/SpareCores/sc-karpenter-nodepool/releases)
(chart and image versions are the release tag without the leading `v`):

```bash
helm install sc-karpenter-nodepool \
  oci://ghcr.io/sparecores/charts/sc-karpenter-nodepool \
  --version <version> \
  --namespace sc-karpenter-nodepool --create-namespace
```

Check that it runs and that the CRD is there:

```bash
kubectl -n sc-karpenter-nodepool rollout status deployment/sc-karpenter-nodepool
kubectl get crd scnodepools.karpenter.sparecores.com
kubectl -n sc-karpenter-nodepool logs deployment/sc-karpenter-nodepool
```

Then create an [SCNodePool](write-an-scnodepool.md). Every chart value, with the
manager flag it sets, is listed in the
[controller reference](../reference/controller.md#helm-chart-values); use
`--set key=value` or `-f values.yaml` as usual.

To install from a clone of the repository instead (for example a development
build), use `charts/sc-karpenter-nodepool` as the chart path and set
`image.repository` and `image.tag`.

Without Helm, `make deploy IMG=<image>` (in the dev container, see
[testing](testing.md)) installs the same controller with kustomize into the
`sc-karpenter-nodepool-system` namespace.

## Where to run it

The controller must not run on a node that Karpenter launches for one of the
pools it generates: if that node is drained, the controller that would repair
the pool goes with it. Schedule it on nodes that are not part of those pools.
The chart's default is a *preference* for nodes without the `karpenter.sh/nodepool`
label, which a managed node group satisfies, but which does not prevent
scheduling onto a Karpenter node when no other node fits. To make it a hard
rule, set `affinity`, `nodeSelector` and `tolerations` yourself:

```yaml
# values.yaml: keep the controller off every Karpenter-launched node
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - {key: karpenter.sh/nodepool, operator: DoesNotExist}
tolerations:
  - {key: CriticalAddonsOnly, operator: Exists}   # if your system nodes are tainted
```

Use `priorityClassName: system-cluster-critical` to keep it from being evicted
before workloads. With `replicaCount: 2` and `podDisruptionBudget.enabled: true`
a second replica waits as a standby (only the leader reconciles).

## Provider notes

### Self-managed Karpenter on EKS (`karpenter.k8s.aws` / `EC2NodeClass`)

Run the controller on the node group that already runs Karpenter (it is not
launched by Karpenter, so the default preference is satisfied). The AWS region
is read from the subnets in the NodeClass status. Nothing else to configure.

### EKS Auto Mode (`eks.amazonaws.com` / `NodeClass`)

All nodes are launched by Auto Mode, so every node carries a
`karpenter.sh/nodepool` label and the default preference has nothing to prefer.
Pin the controller to a pool that is not generated by an SCNodePool, for example
the built-in pools, by excluding the names of your SCNodePools:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: karpenter.sh/nodepool
              operator: NotIn
              values: [web-fast, batch]     # the names of your SCNodePools
```

If you target the built-in `system` pool, add a toleration for its
`CriticalAddonsOnly` taint. Add the egress to the AWS price list: the controller
uses it for the list of instance types Auto Mode can launch and for the
management fee (`price.includeManagedFee`). A custom NodeClass needs an EKS
access entry for its node role, and must not be called `default` (that name is
only available while a built-in pool is enabled).

### AKS Node Auto Provisioning and self-hosted Azure Karpenter (`karpenter.azure.com` / `AKSNodeClass`)

Run on the system node pool. NAP ships a `default` NodePool that overlaps with
generated ones; give generated pools a higher `weight` than it, or disable the
NAP default pools. Never run NAP and a self-hosted Azure Karpenter in one
cluster. The region comes from the node labels (the NodeClass has none).

### Other providers

| NodeClass group / kind | Provider |
|---|---|
| `karpenter.k8s.gcp` / `GCENodeClass` | GCP (cloudpilot-ai, GKE Standard) |
| `karpenter.alibabacloud.com` / `ECSNodeClass` | Alibaba Cloud (official ACK provider) |
| `karpenter.k8s.alibabacloud` / `ECSNodeClass` | Alibaba Cloud (cloudpilot-ai) |
| `karpenter.hetzner.cloud` / `HCloudNodeClass` | Hetzner (stubbi, echohello) |
| `karpenter.itsh.dev` / `HCloudNodeClass` | Hetzner (itsh-cloud) |
| `karpenter.k8s.upcloud` / `UpCloudNodeClass` | UpCloud (kubekanvas) |
| `karpenter.ovhcloud.sh` / `OVHNodeClass` | OVHcloud Managed Kubernetes |
| `karpenter.vultr.com` / `VultrNodeClass` | Vultr |

On self-managed clusters run the controller on any non-Karpenter node, with the
tolerations your control-plane or system nodes need. The provider is chosen from
`nodeClassRef.group` of the SCNodePool's template, so one controller serves
SCNodePools of several providers in one cluster. A group that is not in the
table makes the SCNodePool `Ready=False` with reason `UnsupportedProvider`. The
data each provider needs, how the cloud region is detected and the capacity
types and architectures each one can launch are in the
[v1 overview](../plans/v1/wip/00-overview.md#5-provider-discovery).

## RBAC for NodeClass groups

The controller reads the NodeClass of every SCNodePool to find the cloud region,
and the NodeClaims and nodes as a fallback. The chart's ClusterRole therefore
grants `get`, `list` and `watch` on the NodeClass kind of every supported
provider (rules for CRDs that are not installed are harmless; the controller
looks for new CRDs every five minutes, `nodeClassDiscoveryInterval`). It also
needs `create`, `get`, `list`, `patch`, `update` and `watch` on `karpenter.sh`
NodePools, read access to NodeClaims and nodes, and write access to the
`SCNodePool` objects and their status.

To grant only the groups you use:

```yaml
rbac:
  nodeClassGroups: [karpenter.k8s.aws]
```

A group that is left out cannot be read, so SCNodePools of that provider fall
back to node labels for the region. Extra rules (for example for a provider
fork with another group) go to `rbac.extraRules`.

The chart also creates the ClusterRoles `…-scnodepool-admin`, `-editor` and
`-viewer` for the people who manage SCNodePools (`rbac.userRoles.create`); bind
them yourself:

```bash
kubectl create clusterrolebinding platform-scnodepool-editors \
  --clusterrole=sc-karpenter-nodepool-scnodepool-editor --group=platform-team
```

## Keeper API key

Anonymous access to the Keeper API works (Keeper limits anonymous requests to
three regions each, which the controller respects). If Spare Cores gave you an
API key, store it in a Secret and reference it by name, so the
key is not part of the release values:

```bash
kubectl -n sc-karpenter-nodepool create secret generic keeper-credentials \
  --from-literal=api-key="${KEEPER_API_KEY}"
helm upgrade sc-karpenter-nodepool oci://ghcr.io/sparecores/charts/sc-karpenter-nodepool \
  --version <version> --namespace sc-karpenter-nodepool --reuse-values \
  --set keeper.apiKey.existingSecret=keeper-credentials
```

The Secret is mounted as a file (`--keeper-api-key-file`); a different key name
is set with `keeper.apiKey.key`. Pointing `keeper.url` at a mirror or a caching
proxy is possible for clusters without direct internet access; a proxy for the
controller itself goes into `extraEnv` (`HTTPS_PROXY`).

## Metrics

The chart serves Prometheus metrics over HTTPS on port 8443, behind
authentication and authorisation (`metrics.secure`), through the Service
`<release>-metrics`. Let your Prometheus read them by binding its service
account, and, with the Prometheus Operator, create a ServiceMonitor:

```yaml
metrics:
  readers:
    - {kind: ServiceAccount, name: prometheus-k8s, namespace: monitoring}
serviceMonitor:
  enabled: true
  labels: {release: prometheus}
```

The metrics are described in the [controller reference](../reference/controller.md#metrics).

## Upgrade and uninstall

```bash
helm upgrade sc-karpenter-nodepool oci://ghcr.io/sparecores/charts/sc-karpenter-nodepool \
  --version <new-version> --namespace sc-karpenter-nodepool
```

The CRD is part of the chart's templates (not Helm's `crds/` directory, which is
never upgraded), so an upgrade applies schema changes. The `SCNodePool` API is
`v1alpha1`: read the release notes before upgrading across versions.

`helm uninstall` removes the controller but **keeps the CRD** (`crds.keep`),
the SCNodePools and the NodePools they generated: Karpenter keeps running them,
they are just no longer refreshed. Deleting the CRD (`kubectl delete crd
scnodepools.karpenter.sparecores.com`) deletes every SCNodePool and, through
their owner references, the generated NodePools, so Karpenter drains their
nodes. Set `deletionPolicy: Orphan` on an SCNodePool first (while the controller still
runs) to keep its NodePool.
If you manage the CRD yourself (`kubectl apply -f config/crd/bases`), install
with `--set crds.install=false`.
